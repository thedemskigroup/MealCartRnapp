# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Meal Cart** — an Expo / React Native app (Expo SDK 54, RN 0.81, React 19, New Architecture) for meal planning, meal plans, and shopping lists, with a **Kroger** grocery integration. The backend is entirely **Firebase** (Auth, Firestore, Storage, Cloud Functions, Hosting).

npm start                 # expo start
npm run ios               # expo run:ios      (builds + runs native)
npm run android           # expo run:android
npm run web               # expo start --web

npm run lint              # expo lint (ESLint flat config, eslint-config-expo)

- **This is NOT an Expo Go project.** It uses native modules, a custom config plugin (`plugins/withGoogleSignInIOS.js` — Google/bundle URL schemes + Podfile/AppDelegate tweaks), and `newArchEnabled`, so it requires a **dev client** (`expo-dev-client`). Use `expo run:ios/android` or an EAS build (profiles in `eas.json`).
- `ios/` and `android/` are **gitignored** — they are generated by `expo prebuild` from `app.json`. Never hand-edit them; change `app.json` or the plugin instead.
- **No test framework is configured** (there is no `test` script). Do not assume Jest/RTL exist. With no tests, `npx tsc --noEmit` is the only automated check — it currently reports **7 pre-existing** errors (`IntroScreen.tsx`, `AddItemToList.tsx`, `FilterModal.tsx`, `ProgressBar.tsx`, `assets/svg/IconUpDown.tsx`), so filter to the files you touched. `eslint .` is **not** clean: it reports **9 pre-existing errors** — `react/display-name` in `BaseButton` / `BaseOTPField` / `CreateMealBottomSheet` / `CreateNewListBottomSheet` / `GradientText`, `react-hooks/rules-of-hooks` in `SigninViewModel` / `SignupViewModel`, and `no-undef` in `functions/src/krogerAuth.js` — plus ~180 warnings (mostly `no-unused-vars`). Lint the files you touched (`npx eslint <path>`), not the repo, or you will inherit someone else's failures.
- **`npm run reset-project` is the untouched create-expo-app starter script — it moves `app/` aside and scaffolds a blank one. Never run it.** `README.md` is likewise unmodified boilerplate and describes nothing about this app; ignore it.
- **React Compiler is on** (`experiments.reactCompiler` in `app.json`). Don't add `useMemo`/`useCallback` purely for memoization, and be aware that mutating values captured in render can behave differently than in an uncompiled build.
- OTA updates are configured (`expo-updates`, `runtimeVersion.policy: "appVersion"`), so a JS-only change ships to installed builds via EAS Update while native changes need a new build. **But every build made before 2026-08-13 has `channel: null`** (`eas.json` defined no `channel` until then), and `eas update` can only reach a build that carries a channel. So the 1.0.0 builds already in the stores and on testers' devices can *not* be hotfixed — they need a new build and release. Builds made from the current `eas.json` onward are reachable via `eas update --branch <development|preview|production>`. Verify with `eas build:list --json` before promising a JS-only fix can ship OTA.
- **The user-facing `version` in `app.json` must be bumped for every store release.** `eas.json` sets `appVersionSource: "remote"`, but EAS manages only `versionCode` / `buildNumber` remotely (`eas build:version:get`) — `version` (Android `versionName`, iOS `CFBundleShortVersionString`) always comes from `app.json`. It sat at `1.0.0` from build 17 through 21: App Store Connect will not accept a new *build* of an already-released version as an update (build 19 could only reach TestFlight), so existing iOS users were never offered the update, and on Play the update installed but reported the same version name. Bump `version` once per **public release** (1.0.1 for the current one) — *not* per build: TestFlight and the Play internal track only need a higher build number/`versionCode`, which `autoIncrement` supplies, so many internal builds can share one `version`. Note the coupling: `runtimeVersion.policy` is `appVersion`, so bumping `version` also moves the runtime version — an `eas update` only reaches builds made from the *same* `version`. **The client does the production push** (promoting an internal-testing build in App Store Connect / Play Console) and can only *pick* a build, never change its version — so any build handed to internal testing must already carry the version number they will release. Bump `version` at the start of each release cycle (as soon as 1.0.1 is live, move to 1.0.2) so every handed-over build is promotable. `npm run build:android` automates that bump (always increments the patch first); `npm run build:ios` deliberately does *not* bump, so an iOS build run after an Android one ships the same `version`. The bump has to happen locally before `eas build` archives the project — `prebuildCommand` and `postinstall` run on the ephemeral EAS builder, where an edit to `app.json` is thrown away — so it only fires via these npm scripts, not a bare `npx eas build`. The bump itself is `scripts/bump-version.js` (rewrites just the `version` line in `app.json` + `package.json`, so their formatting survives); `BUMP_LEVEL=minor|major` overrides the patch default.

### Android signing fingerprints & Google Sign-In

Google Sign-In on Android authenticates the *app*, not just the user: Play services checks `(package name, signing certificate SHA-1, OAuth client)` locally and fails with `DEVELOPER_ERROR` (status code `10`, surfaced by the native module as `error.code === "10"`) before any network call. So it is **deterministic per build, never flaky** — an intermittent report means different builds, not a race.

Every certificate that ever signs the app therefore needs its SHA-1 registered on the Firebase Android app `com.app.mealcart` (`1:107165390600:android:49c72691b58601b005febd`). Currently registered:

| SHA-1 | Signs |
| --- | --- |
| `a741c507bca1acf510198bac94f7fd0a2a7517c8` | Google Play app signing key — every install from any Play track |
| `fa87b9eb2a48a9ce1f163d39bd6d181c820da515` | EAS upload keystore — `preview` / `development` APKs |
| `720246de7f9d5c460fe1c02bd612fde62dc13e1f` | one developer's local `~/.android/debug.keystore` (`expo run:android`) |

- **`.aab`s are re-signed by Google Play**, so the upload key's SHA-1 does *not* cover store installs — the Play app signing key (Play Console → Protected with Play → App signing) is a separate fingerprint and must be added too. This was the cause of production Google Sign-In failing while EAS internal builds worked.
- **Each developer's debug keystore is unique to their machine**, so `expo run:android` needs that machine's SHA-1 added: `keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android`.
- Registration is **server-side and takes effect without a rebuild** (the client authenticates with `webClientId`, so `google-services.json` is not consulted for this). `firebase apps:android:sha:create <appId> <sha1>` / `:list` manage it; re-download `google-services.json` afterwards only to keep the repo in sync.
- The project also contains a stale second Android app for the old package `com.jbehl23.mealcart` (`…android:359e7590045873b305febd`) and a stale second iOS app. Adding fingerprints to the wrong app looks like a fix and changes nothing.
- **iOS has no certificate binding** — Google Sign-In there keys off the bundle id and the reversed-client-id URL scheme (`iosUrlScheme` in `app.json`, `IOS_CLIENT_ID` in `services/googleSignIn.ts`, `REVERSED_CLIENT_ID` in `GoogleService-Info.plist` — all three must agree). `DEVELOPER_ERROR` is Android-only.

### Build-breaking config hazards

Two failures here look like application bugs and are not. Check both before debugging a bundle.

- **`babel.config.js` has been a recurring malware target, and a hand-cleanup truncated it.** The history carries three separate payload removals (`8dadda7`, `a65c77e`, `5b34398`); the last one deleted the exported function's closing `};` along with the appended blob, leaving the file unparseable. Because Babel transforms every module, the failure surfaces as `SyntaxError: Unexpected end of input` attributed to **`node_modules/expo-router/entry.js`** — the first file transformed — not to the config, and `expo export:embed` exits 1 with no other clue. Every build from `develop` failed for two days on this. If a bundle dies on the entry file, `node --check babel.config.js` first. Prefer `git checkout` of a known-good revision over hand-deleting a payload, and note the tripwire (`node scripts/scan-supply-chain.js`, also wired into CI) reports **clean** here — a removed payload leaves nothing to find, while the file it left behind still breaks the build.
- **`ios/.xcode.env.local` pins an absolute Node path and goes stale on every Node upgrade.** It is generated, gitignored, and machine-local. When the pinned Homebrew Cellar path disappears, every Pods script phase that shells out to Node (Hermes, RNDeps, expo-updates) fails with `No such file or directory` and the build dies before compiling. Point it at the stable symlink instead: `export NODE_BINARY=/opt/homebrew/bin/node`.
- `expo run:ios` fails to start a dev server if port 8081 is taken by another project and, being non-interactive, skips it rather than prompting. Pass `--port <n>` (the port is baked into the build, so the app looks for that one).

## Architecture

### Navigation — expo-router gated by Redux (hybrid, non-obvious)

Entry is `expo-router/entry` → `app/_layout.tsx` (`RootLayout`), which mounts all providers (Redux `Provider`, `TourStepProvider`, `TourGuideProvider`, `KeyboardProvider`, `FontProvider`) and renders `navigation/RootNavigator.tsx`.

Rather than gating auth through the file tree, `RootNavigator` reads `auth.isAuthenticated` from Redux and renders **either** `AuthNavigator` **or** `AppNavigator`, each a plain expo-router `<Stack>`. So:

- Screens physically live under `app/`: `app/screens/*` (auth flow), `app/(tabs)/*` (main tabs + nested `home/`), `app/appscreens/*` (detail/modal screens).
- **`<Stack.Screen>` registration is per-screen options, not a whitelist.** expo-router routes every file under `app/` regardless, and many existing registrations use names that don't match their route (`AuthNavigator` lists `"SignIn"` for `app/screens/SignIn.tsx`; `AppNavigator` lists `"CreateMealPlan"` for `app/appscreens/CreateMealPlan.tsx`; `app/(tabs)/home/_layout.tsx` lists `"HomeScreen"`/`"DietaryPreferencesScreen"` for files named `index.tsx`/`DietaryPreferences.tsx`). Those entries are inert. A new screen works from the file alone — register it only if you need options, and then use the **real** route name.
- Navigate with the helpers in `utils/Navigation.ts` (`pushNavigation`, `replaceNavigation`, `resetAndNavigate`, `backNavigation`) using the route constants in `constants/AppRoutes.ts` (`APP_ROUTES`) — not raw `router` calls or string paths. `APP_ROUTES` also has stale entries (e.g. `FIRST_SCREEN` → a nonexistent `/screens/FirstScreen`), and not every screen is listed, so verify a constant before trusting it.
- Typed routes are enabled, but the helpers cast to `any` — so a wrong path is a runtime no-op, not a type error.

### State — Redux Toolkit + redux-persist

- Store: `reduxStore/store.ts`. Slices: `auth`, `home`, `ingredientCategory`, `meal`, `profile`, `plans`, `shopping`.
- **Only the `auth` slice is persisted** (redux-persist whitelist, AsyncStorage backend).
- The `LOGOUT` action resets the **entire** store (root reducer sets `state = undefined`).
- `serializableCheck` is **disabled** (Firestore Timestamps/Dates flow through state).
- Always use the typed hooks from `reduxStore/hooks.ts`: `useAppDispatch`, `useAppSelector`.
- Constants are centralized: action-type/slice-name strings in `reduxStore/actionTypes.ts`; Firestore collection names, form field keys, and enums in `reduxStore/appKeys.ts`.

### MVVM layering

Data flows **View → ViewModel → Slice thunk → Service → Firebase**. Respect these boundaries:

- **Slices** (`reduxStore/slices/*`) contain `createAsyncThunk`s that hold business logic and call services. This is the model layer.
- **ViewModels** (`viewmodels/*ViewModel.ts`) are custom hooks (e.g. `useMealsViewModel`) that select state and expose action wrappers. Convention: wrappers take **`onSuccess`/`onError` callbacks** and inspect `thunk.fulfilled.match(resultAction)`. Screens consume viewmodels, never slices/services directly.
- **Services** (`services/*`) are thin Firebase wrappers:
  - `firebase.ts` — initializes app/auth (AsyncStorage persistence)/`db`/`functions` (region `us-central1`)/`storage`. Firebase config is hardcoded here.
  - `firestore.ts` — generic CRUD + cursor pagination (`queryDocuments`), subcollection helpers, `uploadImageToFirebase`.
  - `waitForAuth.ts` — `waitForAuthReady` / `waitForAuthInitialized`; await these before server-backed flows that need `auth.currentUser` after a cold start.
  - `googleSignIn.ts`, `appleSignin.ts` — social auth. `authLink.ts` — the shared guest-upgrade helper both call.
  - `passwordReset.ts` — the only place that may call `sendPasswordResetEmail` / `confirmPasswordReset`.
  - `krogerApi.ts` — `httpsCallable` wrappers for the Cloud Functions, **plus some direct `fetch` calls to `api.kroger.com`** (see the Kroger section below).

### Firestore data model

Collection names live in `reduxStore/appKeys.ts`; access is enforced by `firestore.rules` (composite indexes in `firestore.indexes.json`).

- `meals/{id}` — owned by `uid`. **Global/official meals** use the sentinel `uid == "global"` (`GLOBAL_MEALS_UID`) + `isGlobal == true`, and are readable by every signed-in user. Writing them is **not** admin-only: `canWriteGlobalMeal()` in `firestore.rules` allows any signed-in **non-anonymous** user, and the `isAdmin()` helper sits next to it unused as the commented-out stricter alternative. The UI entry point is the "Add Meal to Firebase" button on Home, behind the `SHOW_ADD_GLOBAL_MEAL` flag in `app/(tabs)/home/index.tsx` — **currently `false`**, and flipping it to `true` is the only switch needed (it routes to `APP_ROUTES.CREATE_MEAL` with `mode: "global"`, and `CreateMealBottomSheet` applies the sentinel uid + `isGlobal` on save). It is additionally gated on `!isGuest`, since the rules reject anonymous accounts and the save would otherwise fail only at submit. Flipping the flag exposes the shared catalog to *every* real user, so re-check that before shipping it on.
- **Meal search matches at word boundaries only, via a token array.** `searchMeals` / `searchGlobalMeals` filter `nameCharacters array-contains <query>`; the tokens come from `buildNameSearchTokens` in `utils/searchTokens.ts`, which indexes the prefixes of **every word-boundary suffix** of the name — so "chicken egg roll" matches "chick", "egg", "egg roll" and "roll", but never a mid-word fragment ("hicken"). Both sides must go through `normalizeSearchText` (lowercase, collapse whitespace, trim) or a double-spaced query misses. `CreateMealBottomSheet` writes the tokens on create **and** on edit, and `updateMealInDb` whitelists the fields it sends, so `nameCharacters` has to stay in that whitelist for a rename to re-index. Meals written before this scheme carry the older whole-name prefixes (a subset of the new tokens, so no regression) until re-indexed with `npm run reindex:meals` (`scripts/backfill-meal-search-tokens.js`, admin SDK, `--dry-run` supported; it holds a plain-JS copy of the token builder that must be kept in sync). Composite indexes for both variants are already declared in `firestore.indexes.json` (`nameCharacters + uid + createdAt` and `isGlobal + nameCharacters + createdAt`).
- `mealIngredients/{mealId}` doc **+ `ingredients` subcollection** = the source of truth for a meal's ingredients, joined onto meals **client-side** by `enrichMealsWithIngredients` in `mealsSlice.ts`. An ingredient is either Kroger-linked (`isKroger`) or references `ingredientCategory`.
- `plans`, `shoppingList` — private per user (`uid`).
- `mealPlan` — per-user, plus shared defaults where `uid == ""`.
- `users/{uid}` — profile doc; document id **is** the auth uid.
- `ingredientCategory`, `ingredients`, `dietryPreferences` (note the misspelling — it's real) — shared read-only reference data, admin-writable only. The admin allowlist is an email list in `firestore.rules`.

### Plans & shopping-list domain rules (not derivable from types)

- **`MealStatus`** (`reduxStore/appKeys.ts`) is `CREATED | STARTED | RESUMED | PAUSED | COMPLETED`. There is **no `UPCOMING`** — "upcoming" is derived purely from `startDate` vs today.
- **Several plans may be `STARTED` at once** (so a user can pull a shopping list for a plan before it begins). `plans.activePlan` is still a *single* slot: it is the `STARTED` plan **whose `days[]` include today** (`pickActivePlanForToday` in `planSlice.ts`), and it is `null` when no started plan covers today. Home shows only that plan; the Plans tab renders **every** `STARTED` plan. Anything new that assumes one started plan will silently pick an arbitrary one.
- **Shopping-list items are untyped extras.** The runtime docs use an `ingredients` array whose fields (`acquired`, `isKroger`, `krogerIngredientId`, `count`) are **absent from the declared `ShoppingListItem` interface** — it declares `items`/`isChecked` instead. Trust the runtime shape written by `CreateNewListBottomSheet.tsx`, not the interface.
- **`AddItemToList` (the "add extra item" modal) auto-adds, and spans both meal collections.** Checking a meal immediately puts *all* of its ingredients into the added list — there is no per-ingredient "pending → Add" step any more (the `pendingItems` stage was removed, because the first tap looked like it did nothing and `handleGenerateList` only ever read the added list). An effect keyed on `dynamicIngredients` keeps the two in sync: unchecking a meal drops its ingredients, and anything removed with the ✕ is held in `removedNames` so the effect doesn't resurrect it when `meals` grows through pagination. The meal list, its pagination (two cursors — the user's own meals first, then the global catalog) and its **search** all cover user *and* global meals; the search fires `searchMealsCombined` and `searchGlobalMealsCombined` in parallel and merges by id, each resolving to `[]` on failure so one side failing still shows the other. Ingredient lookup must therefore read `[...meals, ...globalMeals, ...filteredMeals]` — miss `globalMeals` and a checked global meal silently yields zero ingredients. The same modal backs `CreateMealPlan` (`from === CREATE_MEAL_PLAN`, which switches it to single-select), so changes here hit both flows. Caveat: the unit stepper only renders on *suggestion* rows, so auto-added ingredients ship with their default unit unless you ✕ one and re-add it.
- **"Add item Manually" searches the Kroger catalog**, using the store on the user's Kroger connection (`getKrogerConnectionStatus().selectedStore`) and `searchKrogerProducts` — the same source the meal builder's ingredient search uses. It previously filtered only the *selected meals'* own ingredients, and since checking a meal auto-adds every one of them, that pool was always empty and typing could never return anything. Picks are held in a separate `manualKrogerItems` state (not `fullIngredientsData`, which is recomputed from the selected meals and would drop them) and their rows are flagged `manual: true` so the auto-add sync effect does not sweep them away. `handleGenerateList` resolves added names against both sources. With no Kroger store selected the block says so rather than failing silently.
- In `TestPlanShopping.tsx`, checkbox selection is tracked as composite string ids (`${ingredientId}-${mealId}-${index}`) keyed to the **flat `allIngredients` index**, while `acquired` separately records what was already sent to Kroger. Keep those two concepts distinct: selection drives *what to send*, `acquired` drives the progress bar.
- **Sending to Kroger requires a modality, and that requirement caused the longest-running "Kroger transfer is broken" report.** `krogerModality` starts `null`, and Delivery / Pickup are a single mutually-exclusive value that also toggles *off* when the selected one is tapped again — so it is easy to be back at `null` without noticing. The Send button is `disabled` until one is picked, which is correct and intended; what was broken is that it kept the **enabled style while disabled**, so it looked like a live button and silently swallowed every tap. No handler ran, no request was made, no error appeared, and every server-side log was legitimately empty — which reads as a backend failure and is not one. It also made the handler's own `testPlanShopping_krogerSelectModality` alert unreachable. If a transfer is reported as doing nothing, **confirm a modality is selected before investigating anything else.**

### Kroger integration (secrets server-side; some calls go direct)

**Secrets** (client id/secret) live only in Cloud Functions — but the app is *not* purely proxied. There are two paths, and it matters which you use:

1. **Via Cloud Functions** — OAuth, connection status, store selection, and generic requests through `krogerProxy`.
2. **Direct from the client** — `krogerApi.ts` fetches a short-lived user OAuth token via the `getKrogerUserToken` callable, then calls `https://api.kroger.com` **directly**: `GET /v1/cart`, and `PUT /v1/cart/add` in `addItemsToKrogerCart`. So cart writes do **not** pass through a function, and `functions/src/config.js`'s path allowlist (`/v1/cart`) does not constrain them.

- `index.js` exposes `createKrogerAuthSession`, `getKrogerConnectionStatus`, `krogerProxy`, `krogerOAuthCallback`, `getKrogerAppToken`, `getKrogerUserToken`, `saveKrogerSelectedStore`, `disconnectKrogerAccount`, `logKrogerCartAttempt`.
- `krogerAuth.js` (token lifecycle), `krogerApi.js` (server request wrapper), `config.js` (base URL, redirect URI, path allowlist).
- OAuth redirect `https://mealcart-5d62b.web.app/kroger/callback` is rewritten to the `krogerOAuthCallback` function via the Hosting rewrite in `firebase.json`, which then deep-links back into the app (scheme `mealcartrnmain`).
- Secrets are `defineSecret("KROGER_CLIENT_ID" / "KROGER_CLIENT_SECRET")`. See `docs/kroger-firebase-setup.md` and `docs/kroger-file-map.md`.

#### Cart writes: the observability blind spot, and how to read it

A user reporting "it doesn't send items to my cart" produced **zero** server-side evidence for days. The cause was ultimately UI-side (the modality gate in the plans/shopping section above), not anything here. What follows is the observability gap that made it undiagnosable, plus the request-shaping rules — flagged individually where a claim is confirmed and where it is only assumed:

- **Only the token mint is visible in `firebase functions:log`; the cart request itself is not.** It goes straight from the device, so nothing else about it reaches Cloud Logging. `logKrogerCartAttempt` exists purely to close that gap — `addItemsToKrogerCart` posts the outcome (`batch-ok` / `partial` / `all-rejected` / `request-failed`, plus rejected UPCs and Kroger's stated reason) and never the token. Read it with `firebase functions:log --project mealcart-5d62b --only logKrogerCartAttempt`. It only reports from a build carrying the client change, so an older build still shows nothing.
- **`addItemsToKrogerCart` retries item-by-item after a batch rejection — but the premise behind that is UNVERIFIED.** The assumption is that Kroger validates `PUT /v1/cart/add` as a single unit, so one unacceptable item (e.g. a UPC the user's selected store does not carry) fails the whole request and nothing reaches the cart. That was a hypothesis formed to explain a "nothing arrives, no error" report; the report turned out to have a UI cause (the modality gate, above) and **the batch behaviour was never actually observed or tested**. Treat it as untested until someone confirms it against the API. The retry is harmless and does improve the error message — it returns `{ addedUpcs, rejected }`, and only `addedUpcs` may be marked `acquired` — but do not cite it as documented Kroger behaviour, and do not build anything new on it without checking first. A 401/403/429/5xx describes the request as a whole and is thrown straight through rather than repeated once per item.
- For the avoidance of doubt, two things Kroger **does** support and which were never in question: `modality` (`PICKUP` / `DELIVERY`) per item, and single-item requests.
- **A recipe amount is not a cart quantity, and sending it as one over-buys wildly.** "3 tablespoon olive oil" ordered *three bottles*; "3 piece chicken breast" ordered *three packs*; a 29-item list arrived as 39 Kroger items. Cart quantity counts **retail packages**, so `utils/krogerQuantity.ts` (`krogerCartQuantity`) sends **1** for every measured amount and uses the count only when the unit itself names a package the user is counting out (`can`, `package`, `bottle`, `jar`, `bag`, `bunch`, … — matched as whole words, singular or plural, so "canola oil" is not a can). A unit that *starts with a digit* is a size, not a count: `250 ml`, `1 kg` and the Kroger sizes stored verbatim (`16 fl oz`, `12 ct`) all describe one package. **Converting properly is not possible with the data we store** — it needs the package size in the same dimension as the recipe unit, and a shopping-list ingredient carries a single `unit` string that is the recipe unit for the premade catalog but the Kroger `size` for meals built in the app (`CreateMealBottomSheet` writes `meta.size` into `unit`). Under-buying is the safe side: one bottle short is one tap to fix, while three unwanted bottles cost money and **cannot be removed by the app at all** (v1 has no remove endpoint). Rows on `TestPlanShopping` show "Kroger cart: 1" whenever the sent quantity differs from the displayed recipe amount, so this is visible before sending.
- **One entry per UPC.** The same product can reach a list from two meals, so `TestPlanShopping` merges by UPC. What is summed is *packages*: measured amounts contribute one package each and do not add up (two meals both using olive oil still need one bottle), while counted package units do (`2 can` + `1 can` = 3). Merging is right on its own terms — one line of 2 expresses the intent better than two lines of 1 — but note the original justification, that Kroger *rejects* duplicate UPCs in one request, is **untested**, same as the batch assumption above.
- **Items added through the API reach the Kroger *account* but the Kroger *app* may keep showing a stale cart** until the cart is touched on kroger.com (reported from the field, 2026-09-17; the same send is visible on the web immediately). Nothing in this app can flush that cache — the write has already succeeded — so a "the items never arrived" report should be checked on kroger.com before it is treated as a transfer failure.
- **Sending is additive, and v1 has no remove endpoint.** Every send appends another copy of every selected item — this is how one list became 276 cart items across repeated attempts — hence the confirmation prompt when any selected item is already `acquired`. A cart can only be emptied by the user in Kroger's own app or website; Meal Cart cannot clear it.
- **Kroger does not echo `scope` in the authorization_code token response, so `scope: ""` is normal and proves nothing.** Do not read an empty scope as "cart write was not granted" — a token with an empty scope adds to the cart perfectly well. (This was misdiagnosed as the root cause once; the actual bug was the UI-side modality gate described above.) `completeAuthSession` used to overwrite the granted scope with the *requested* one, which masked what Kroger returned; it now stores Kroger's value and keeps the request under `requestedScope`, and `getKrogerUserToken` logs both. Nothing in the app branches on the user-token scope, so an empty stored value is harmless.

### Guided onboarding tour

First-run tour uses `rn-tourguide` (patched) coordinated by `context/TourStepContext.tsx`. Because tour steps must trigger UI actions across different screens, the context exposes many `triggerX` / `setTriggerX` callback-registration slots that screens populate on mount. Completion is tracked on `user.hasCompletedTour` (`markTourCompleted` in `authSlice.ts`).

Non-obvious details:

- **`zone` number *is* the step order, and content is index-based:** `TourGuideZone zone={N}` → `tourSteps[N - 1]` in `components/TourTooltip.tsx` (`stepIndex = currentStep.order - 1`). The tour spans zones 1–18 across `app/(tabs)/home/index.tsx`, `app/(tabs)/_layout.tsx`, `2_Plans.tsx`, `3_Lists.tsx`, `CreateMealPlan.tsx`, `CreateNewListBottomSheet.tsx`, `TestPlanShopping.tsx`. **Renumbering or inserting a zone silently reassigns every later step's text**, so keep zone numbers and the `tourSteps` array in lockstep.
- `TourTooltip.tsx` also drives **cross-screen navigation** per step (`handleNextOrNavigate` / `handleBackOrNavigate` switch on `stepIndex`) — so it is control flow, not just presentation.
- **Tooltip placement is patched.** Upstream `Modal.js` positions the bubble with a hardcoded assumed height and no on-screen clamping, which throws tall tooltips off the top of the screen. The patch measures the real height, clamps the tooltip on-screen, and adds two **opt-in per-zone props**: `tooltipBelowZone` (force placement beneath the zone) and `legacyTooltipPosition` (keep upstream math). Any new positioning behaviour should stay **opt-in per zone** — changing the shared math moves every step at once.
- `TourGuideZone` forwards only a **fixed allowlist** of props to the step (see `lib/components/TourGuideZone.js`); a new per-step prop must be added there too before `currentStep` will see it.
- Zones inside `@gorhom/bottom-sheet` and zones using `style={{ flex: 1 }}` measure poorly (relative to the sheet, or as the whole screen), which is why their tooltips need explicit placement props.
- `getTooltipPositionStyle` in `TourTooltip.tsx` is **dead code** (never called) — an abandoned earlier attempt at the fix above. Do not assume it affects layout.
- To retest the tour on an existing account use `resetTour` from `TourStepContext`; it is otherwise gated behind `user.hasCompletedTour`.

### Auth flows (four surfaces, each with its own trap)

**A password account can exist in Auth with no `users/{uid}` doc, and that used to brick it.** `loginAsync` reads the profile doc after a successful credential check; when it was missing it rejected with "User is not registered in the database", while sign-up said `auth/email-already-in-use` and a password reset changed nothing — the account was unusable. It now **re-seeds the doc from the auth user and lets them in**. Keep that behaviour: valid credentials mean the account exists, so a missing doc is our data being out of sync, never grounds to refuse a login.

The original cause was `deleteAccountAsync` (`profileSlice.ts`), which deletes the Firestore doc and *then* the auth user. `deleteUser` throws `auth/requires-recent-login` on a session older than a few minutes — the normal case when deleting from Profile — leaving the account half-deleted. The doc must still go first (after `deleteUser` the client is signed out and `firestore.rules` denies the delete), so it now **snapshots the doc and restores it if `deleteUser` fails**. Any change here must preserve that rollback.

**Forgot-password is an emailed link and cannot be anything else.** Firebase has no "verify a code, then set a password" primitive; `updatePassword` needs a live session (that's the signed-in Change Password screen → `changePasswordAsync`, which reauthenticates first). Everything goes through `services/passwordReset.ts`:

- `sendPasswordReset` **reports success for an unknown address** — otherwise the form is an account-existence oracle, and with email enumeration protection on Firebase doesn't throw `auth/user-not-found` anyway. Don't "fix" this by adding a not-found message.
- **No `ActionCodeSettings`, deliberately.** A continue URL's `android`/`iOS` fields relied on Firebase Dynamic Links, which is shut down, so it would only bounce to a web page (and its domain needs to be on the authorized-domains list). The link therefore opens Firebase's hosted reset page; brand it under Authentication → Templates.
- `completePasswordReset` is unused but correct — it's for the alternative setup where a custom action URL deep-links to `app/screens/NewPassword.tsx` with an `oobCode`.

**`signInOrLinkWithCredential` (`authLink.ts`) is the only social-auth entry point** — it links Apple/Google onto an anonymous guest so their meals and plans survive the upgrade. Three non-obvious requirements, all of which caused real bugs:

- `isAnonymous` and `providerData` are read off the **cached** `User` and lag the server after a link, so it `reload()`s first. Without that, a second attempt in the same session took the link branch on an account that already had the provider and threw `auth/provider-already-linked`.
- It checks `providerData` and skips linking when the provider is already attached, rather than relying on catching that error.
- **Apple and Google identity tokens are single-use.** If a link reaches the server before failing, the credential is spent, so the sign-in fallback prefers `OAuthProvider.credentialFromError(error)` over reusing it.

**Social sign-in has two error surfaces and they must be separated.** `isErrorWithCode` from `@react-native-google-signin` is only a *"has a `code` property"* check, so it is **true for every `firebase/auth` error too**. Funnelling both through one switch sent Firebase errors out via `default: error.message`, which renders as the raw `"Firebase: Error (auth/...)."`, and made the `auth/*` branches after it unreachable. Match `auth/`-prefixed codes **first**, then native codes. Also note the native module reports `DEVELOPER_ERROR` as the bare string `"10"` — `statusCodes` has no entry for it.

- `context/AuthContext.tsx` — a parallel `onAuthStateChanged`-based auth gate; `<AuthContextProvider>` is **commented out** in `app/_layout.tsx`. Auth state lives in the `auth` Redux slice only.
- `models/User.ts` — unused; user/profile types come from `constants/interfaces.ts`.

- `app/screens/NewPassword.tsx` + `NewPasswordViewModel` — unreachable, because the reset link opens Firebase's hosted page rather than deep-linking into the app. Kept (and now actually implemented against `confirmPasswordReset`) for the custom-action-URL setup; it needs an `oobCode` route param to do anything. `APP_ROUTES.NEW_PASSWORD` is likewise unused. ## UI & styling conventions

- **Responsive scaling:** use `moderateScale`, `horizontalScale`, `verticalScale`, `getWidth`, `getHeight` from `constants/Constants.ts` (reference frame 430×932) instead of raw pixel values.
- **Colors** → `constants/Theme.ts` (`Colors`). **All user-facing strings** → `constants/Strings.ts` (`Strings`). **Shared interfaces** → `constants/interfaces.ts`.
- **Path alias:** `@/*` maps to the repo root (`@/components/...`, `@/services/...`).
- **SVGs** are imported as React components (`react-native-svg-transformer`; metro moves `svg` from asset → source ext). Icons live in `assets/svg/`, typed via `declarations.d.ts`.
- **Fonts** load through `context/FontContext.tsx` (`FontProvider` blocks render until fonts resolve) + `utils/Fonts.ts`.
- **Forms:** Formik + Yup; validators in `utils/validators/`.
- **Toasts:** call the helpers in `utils/Toast.ts` (`showSuccessToast`, `showErrorToast`, `showInfoToast`) rather than `Toast.show` directly; rendering is `react-native-toast-message` with the custom `utils/ToastConfig.tsx` mounted in the root layout.
- **Global loader:** `components/Loader.tsx` is mounted once in the root layout and driven **imperatively** via the exported `showLoader()` / `hideLoader()` (module-level singleton, not Redux/props). It auto-hides after 15s as a safety net.
- **Bottom sheets:** `@gorhom/bottom-sheet`.
- **Beware stray `{" "}` in JSX.** A bare string as a direct child of a `View` throws *"Text strings must be rendered within a `<Text>` component"* at runtime — it renders as an error toast rather than a build failure, and one always-mounted instance makes it look like it belongs to whatever screen you are on. Several such literals exist inside `<Text>` (harmless); check the parent before copying the pattern. **A JSX comment on the same line as an element counts**: `<Loader /> {/* </AuthContextProvider> */}` in `app/_layout.tsx` put a permanent error toast over the tab bar on every screen (it even covered the tab bar's touch targets) — the space before the comment is the bare string. Put trailing JSX comments on their own line. The stack trace blames the nearest provider (`FontProvider`), not the offending line.
- **A `disabled` button must carry a disabled style.** `disabled` on a `TouchableOpacity` swallows the tap entirely, so a button that stays visually enabled while disabled is indistinguishable from a broken feature and hides any guard message the handler would have shown. This is exactly how the Kroger send button read as "the transfer does nothing" (see the plans/shopping section). Pair every conditional `disabled` with a conditional style.
- Prefer `minHeight` over a fixed `height` on containers holding user-supplied text (meal/ingredient names). A fixed height clips wrapped text and lets absolutely-positioned children — e.g. a remove "✕" — spill outside the box.
- **Never render such a name in a read-only `<TextInput>`.** A single-line `TextInput` cannot wrap, and it *scrolls* rather than clipping cleanly, so a long Kroger name ("Laura's Lean Beef® 92% Lean All Natural Ground Beef") lost its **beginning** off the left edge — it looked like a truncation bug at the wrong end. Use `<Text>` with `minHeight` + `paddingVertical` so the row grows (this was the added-item row in `AddItemToList.tsx`).
